## Findings

Disposition is stated for every finding. “Fix now” means a proposed remediation or reconciliation
action below; this retrospective does not apply product-code or planning changes.

### A. Spec-to-implementation reconciliation

**A1 — the delivered progress path violates its overflow-safe clamping criterion.** Story 2.3 AC 1–3
requires Remaining never to fall below zero and positive over-progress to clamp at zero and complete.
`WorkItemEffort.Report` first evaluates `Done + doneDelta` and only then calls `Math.Min`
(`src/Hexalith.Works.Contracts/ValueObjects/WorkItemEffort.cs:28-35`). Decimal addition throws when the
sum exceeds `decimal.MaxValue`; therefore a valid positive report against a sufficiently large effort
throws instead of returning the promised clamped result. `git blame` attributes the expression to
Story 2.3 commit `cbf1cba`, and the existing boundary test uses only `7 + 5`
(`tests/Hexalith.Works.UnitTests/WorkItemProgressTests.cs:160-169`). — **fix now; blocking.**

**A2 — the declared “one lifecycle authority” is not actually one authority.** Story 2.1 AC 6 says
later lifecycle stories must reference the matrix rather than choose behavior locally. The matrix
calls itself the single source of truth (`docs/lifecycle-transition-matrix.md:3-11`), but
`ReportProgress`, `ReEstimate`, and `RescheduleWorkItem` each implement their own status policy in
`WorkItemAggregate` (`:277-280`, `:328-331`, `:364-367`) instead of consulting
`WorkItemLifecycle.Decide`. Even for the nine acts that do consult the table, handlers branch only on
`LifecycleOutcome.Decision`; no production code consumes its `Target` value
(`src/Hexalith.Works.Server/Aggregates/LifecycleOutcome.cs:22-31`). A table/handler target mismatch can
therefore compile and pass the current tests. — **fix now; blocking.**

**A3 — current planning material is not a trustworthy description of the delivered epic.** At
`c1ba6bb`, Epic 2 was the five-story delivery recorded in sprint status. The current uncommitted
`epics.md:433-755` instead defines seven differently scoped stories and names contracts not present in
source (`CorrectProgress`, `ProgressCorrected`, `WorkItemReopened`, and a dedicated handoff act). That
rewrite may be a valid future plan, but it cannot serve as the as-built record without an explicit
mapping and provenance boundary. — **fix now (spec reconciliation).**

**A4 — the post-epic requirements disagree on downward re-estimation and add unimplemented bounds.**
Current PRD FR-8/FR-9 says a downward re-estimate leaves `Done > Estimated` visible as overrun
(`prd.md:216,225`), whereas architecture AD-17 says ReEstimate clamps Done (`architecture.md:264-275`)
and current code/tests do clamp it (`WorkItemEffort.cs:38-45`;
`WorkItemReEstimateTests.cs:80-96`). The PRD also added a 1,000-character optional-note bound on
2026-09-08 (`prd.md:197-205`), but the three Epic 2 handlers persist `command.Note` without a bound
(`WorkItemAggregate.cs:300-307,345-354,370-378`). These later requirements are not retroactive Epic 2
acceptance criteria; they are unresolved forward-planning decisions. — **fix now (spec reconciliation
and story the chosen behavior).**

### C. Duplication, pattern divergence, and size

**C1 — matrix, handlers, prose, and tests duplicate the transition policy.** The nine-act switch lives
in `WorkItemLifecycle.cs:21-77`; three more act policies live in `WorkItemAggregate`; the Markdown
matrix repeats all outcomes; and `WorkItemLifecycleTests.cs:42-156` hand-copies the table again. The
fitness test only checks that status and command tokens occur somewhere in the document
(`LifecycleTransitionMatrixDocTests.cs:36-66`), not that cells equal executable policy. This is the
mechanism behind A2. — **fix now with A2.**

**C2 — the catalog is complete today but its completeness proof is circular.** The shared catalog is
a hand-authored 40-item list with a hand-authored `Count = 40`
(`tests/Hexalith.Works.IntegrationTests/WorkItemV1Catalog.cs:15-92`). Registration asserts that same list
against that same count and merely requires the global resolver to contain *at least* 40 derived types
(`WorkItemSerializationRegistrationTests.cs:25-39`). The two golden corpora bind fixtures
bidirectionally to catalog entries, which is strong for listed payloads, but a new decorated contract
omitted from the list can leave the suite green. — **fix now (verification gate).**

**C3 — high churn produced large files, but not an evidenced god class.** The epic changed 83 files
(+6,576/−76). `WorkItemAggregate` received +291 lines during the range and is now 515 lines;
`WorkItemState` received +117 and is now 252. Both remain cohesive around command decisions and replay
respectively. The actionable issue is duplicated policy, not size alone. — **accept as-is; monitor
after A2.**

**C4 — `AttemptedAct` uses two naming grammars.** Lifecycle-table rejections persist short act names
such as `Assign` and `Complete`, while progress/planning/link rejections persist command type names such
as `ReportProgress` and `RescheduleWorkItem` (`WorkItemAggregate.cs:162-179,266,280,331,367,410`). The
Story 2.5 review already recorded this at `orchestration-1-20260615-182114.md:215`. These are now durable
diagnostic values; renaming existing values would itself be a compatibility change. — **accept as-is
for v1, but freeze the mapping as part of A2's tests.**

### D. Independent review lenses

The required review ran three independent lenses over the exact epic diff and commit-subject claims:
adversarial critique, edge cases, and verification gaps. Reports were rechecked against current source;
stale reports were dropped rather than converted into actions.

**D1 — sequence ordinals have unchecked exhaustion boundaries.** `NextSequence` performs
`(state?.Sequence ?? 0) + 1` (`WorkItemAggregate.cs:478-482`). At `long.MaxValue` it wraps; the two-event
progress-completion and spawn-suspend paths can wrap their second event from `long.MaxValue - 1`
(`:118-145`, `:299-315`). That breaks Story 2.2's ordering premise rather than failing explicitly.
There is no maximum-sequence test. — **fix now with A1 as numeric-boundary hardening.**

**D2 — aggregate identity is checked on only one command path.** Of the 15 adapter wrappers, only
`LinkConversation` accepts a `CommandEnvelope` and compares its domain/tenant/aggregate identity
(`src/Hexalith.Works/WorkItemEventStoreAggregate.cs:108-123`); only that pure handler checks established
state identity (`WorkItemAggregate.cs:381-419,491-501`). This is already tracked precisely by
`epic-1-retro-item-4-extend-the-envelope-payload-identity-che`; no duplicate Epic 2 action is added.
— **defer to the existing tracked item.**

**D3 — three focused regression gaps remain.** ReEstimate success is tested only from `InProgress`,
although the documented policy accepts all five live statuses
(`WorkItemReEstimateTests.cs:22-265` versus `docs/lifecycle-transition-matrix.md:101-121`); the exhaustive
lifecycle matrix does not assert `AttemptedAct` for its rejected cells
(`WorkItemLifecycleTests.cs:579-599`); and C2's catalog membership is not derived from the Contracts
assembly. — **fix now through A2/C2.**

**D4 (wins from later hardening) — several diff-only reports no longer hold.** Current source rejects a
duplicate `CreateWorkItem` (`WorkItemAggregate.cs:18-25`), rejects nonzero initial Done (`:34-36`),
retains effort while consuming corrupted negative/mismatched `ReEstimated` events
(`WorkItemState.cs:183-200`), validates unknown executor enum sentinels
(`ExecutorBinding.cs:13-32`), and freezes rejection payloads in both writer and compatibility corpora.
Those reports described the historical diff boundary but are not current findings. — **accept as-is;
later remediation verified.**

## Action items

All items below are proposals for the normal planning/dev loop; no product code or project contract was
changed by this retrospective.

1. **Make progress and payload sequencing overflow-safe.** Compare progress delta with Remaining before
   addition (or use an equivalent saturating operation), define explicit sequence-exhaustion behavior
   for one- and two-event results, and add `decimal.MaxValue`, `long.MaxValue`, and
   `long.MaxValue - 1` tests. **Owner:** Amelia (Dev). **Sources:** A1, D1.
2. **Make the lifecycle authority executable and singular.** Move progress/planning status decisions
   behind the shared policy; make handlers verify/use `LifecycleOutcome.Target`; mechanically compare
   or generate the Markdown matrix; add all-live-status ReEstimate coverage and assert the durable
   `AttemptedAct` mapping for every rejection. **Owner:** Charlie (Senior Dev). **Sources:** A2, C1, C4,
   D3.
3. **Reconcile Epic 2's planning contract before implementing the rewritten scope.** Preserve an
   explicit as-built five-story mapping, label the seven-story material as future/replacement scope,
   decide whether downward re-estimation preserves overrun or clamps Done, and story the chosen
   1,000-character note policy plus any new correction/handoff contracts. **Owner:** John (PM), with
   Winston (Architect) for AD-17. **Sources:** A3, A4.
4. **Derive durable-catalog completeness from the Contracts assembly.** Fail when a decorated command,
   success event, or rejection has no catalog sample, stable discriminator, and both required golden
   representations; keep fixture↔catalog checks bidirectional. **Owner:** Dana (QA). **Source:** C2,
   D3.

Existing Epic 1 items 2, 4, and 13 remain the owners for the SDK gate, cross-command identity, and
skipped-retro escalation respectively; they are intentionally not duplicated here.

## Acceptance verdict

**Rejected — declared criteria.** All five stories are marked `done`, and the current Release build,
568 unit tests, 3 property tests, and 45 focused integration tests pass. Those green paths do not cover
two unresolved failures against the declared criteria:

1. Story 2.3's promised positive-delta clamping can throw on decimal overflow before clamping (A1).
2. Story 2.1's explicit requirement that later lifecycle behavior use one authority is contradicted by
   three local handler policies and a token-only documentation gate (A2/C1).

Unchecked sequence exhaustion (D1) is an additional blocking ordering risk. With no human override,
the retrospective rules require a rejected verdict while a blocking criterion failure remains. The
`epic-2-retrospective` sprint key will still become `done`; that key records that this retrospective
ran, not that the epic passed.
