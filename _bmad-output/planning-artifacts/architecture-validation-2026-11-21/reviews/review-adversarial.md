# Adversarial architecture review

Reviewed Works architecture SHA-256 `e53447b83e031c5ef39e9f1e443cdf311a7db164d31f43a36bb0b3693a7609ab` on 21 November 2026. Two high-severity design decisions are open for registry-driven work. One medium-severity clarification affects current projection integrations. The review used source inspection and event interleavings.

## High · Order parent termination and reservation acceptance

FR-10 rejects new reservations once parent termination is accepted. AD-21 obtains a witness inside the parent turn, checks it immediately before registry dispatch, and reserves the edge inside a different aggregate turn. Consider a valid parent witness, followed by dispatch, a durable parent cancellation, then the registry's `EdgeReserved`. One implementation treats the validated witness as prior admission and completes attachment plus catch-up. Another considers the registry append the acceptance boundary and rejects the same request. The two implementations produce different child streams. Catch-up can terminate a child but cannot undo an inadmissible creation. The registry's single-writer checks settle disputes between two parents over one child. They do not order a registry append against a parent termination. [AD-21](../../architecture.md#L440) · [PRD FR-10, lines 247–249](../../prds/prd-works-2026-06-14/prd.md#L247)

**Decision for Works and EventStore.** Define one durable acceptance point relative to termination. If parent admission orders both, persist the admitted operation in the parent turn and make it discoverable and replayable through a crash before the registry append. If registry reservation is acceptance, specify how termination fences that commit. Exercise both orderings and a crash between the two turns. The existing concurrent-parenting gate remains appropriate until this ordering is qualified. [AD-21, lines 419–448](../../architecture.md#L419) · [Work-tree gate, line 706](../../architecture.md#L706)

## High · Bind a trusted child Resume to the intended wait at the parent

AD-21 requires delayed work for a consumed wait to leave a later suspension alone. AD-13 matches a Resume against the current kind and key. Suppose a parent waits on a child or a date. The Reactor dispatches a child Resume, the date wins, and the parent suspends again on the same child before the first delivery of that child Resume. One consumer sees a matching condition and resumes the second wait. Another checks which wait the effect was issued for and closes it as obsolete. The current command carries tenant, item and condition. Its handler matches by condition, and the translator reads the parent before submission. AD-26 replay protection cannot distinguish this case at first delivery, when no receipt exists for the delayed effect. The PRD fixes the required behavior. The target contract still needs a target-turn witness. [AD-13, lines 249–260](../../architecture.md#L249) · [AD-21, lines 450–455](../../architecture.md#L450) · [FR-15, lines 318–328](../../prds/prd-works-2026-06-14/prd.md#L318) · [Resume contract](../../../../src/Hexalith.Works.Contracts/Commands/ResumeWorkItem.cs#L11) · [Parent handler](../../../../src/Hexalith.Works.Server/Aggregates/WorkItemAggregate.cs#L241) · [Child translator](../../../../src/Hexalith.Works/Recovery/WorksProcessTranslator.cs#L169)

**Decision for Works and EventStore.** Bind the trusted reconciliation effect to the issuance of that parent wait, and compare the binding inside the serialized parent turn before clearing conditions. Specify a stable disposition for an obsolete wait and retain it across retries. Test first delivery after the identical condition has been installed a second time, and replay that disposition after restart.

## Medium · Label current and target projection key formats

AD-06 labels its `works:v3:tenant:…` roll-up key as a registry-backed target. AD-15 states that tenant state begins with the same prefix under a mixed CURRENT/TARGET heading. A query implementer following AD-15 could pass the encoded target key to the current SDK. The canonical writer and reader use a tenant-scoped `SharedProjectionScope` and logical key `works-runtime-v3:rollup:{item}`. The SDK derives the physical manifest and generation keys. Both integrations can respect tenant isolation and use one generation yet look up different documents. [AD-06, lines 154–165](../../architecture.md#L154) · [AD-15, lines 279–291](../../architecture.md#L279) · [Logical key](../../../../src/Hexalith.Works/Projections/WorksReadModelKeys.cs#L32) · [Query path](../../../../src/Hexalith.Works/Queries/GetWorkItemQueryHandler.cs#L105) · [SDK scope](../../../../references/Hexalith.EventStore/src/Hexalith.EventStore.Client/Projections/SharedProjectionScope.cs#L39)

**Clarification.** Label the encoded tenant/control namespace as target-only. Point current adapters to `WorksReadModelKeys`, the scope and the SDK coordinator. Make reader/writer agreement on the key format part of the existing migration gate.
