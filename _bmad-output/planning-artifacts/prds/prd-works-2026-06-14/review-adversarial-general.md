# Adversarial Review — Hexalith.Works PRD

## Preamble

The PRD's two bets — "everything is a Party" and "AI in the loop but never in the system-of-record" — are both declared proven by v1 while v1 ships nothing that could disprove them: no adapter inspects the Channel, no policy reads the AuthorityLevel, no interpretation is ever projected, and every Success Metric reduces to "the build is green under Aspire." Underneath that, the document's purity rules (a clock-free, single-aggregate `Handle`) are incompatible with three behaviours it also mandates (spawn-with-parent-link, child-completion resume, cascade-cancel), and it names an undefined "engine" to paper over the gap. With implementation several epics in, every one of these ambiguities has already been resolved *somewhere* by an engineer — the FR-20 correct-course shows the pattern — and the PRD as written cannot tell you whether that resolution is compliant.

## Findings

- **[critical]** The keystone binding cannot hold the roles the roadmap needs, and SM-3 cannot fail in v1 (§4.5 FR-17/FR-19, §11 SM-3, §12) — FR-17 gives a Work Item "its single Executor Binding"; FR-19's proposed set includes `Read = await/observe` and `Administer = approve spend, set caps, cancel`. A single slot cannot carry a Contributor doing the work *and* an Administer approving its spend, an observer, or an escalation ladder's next rung — exactly the Theme 4/6 shapes §12 claims this seam enables. Meanwhile "no domain code branches on executor kind" is trivially true of a kernel that stores three fields and never reads them; the branching moves into adapters (an email Channel needs a magic link, MCP does not) where SM-3 does not look. *Fix:* Either make the binding a set (one primary Executor plus zero-or-more role bindings) now, or state explicitly that approvers/observers are *not* bindings and name where Theme 6 will put them. Rewrite SM-3 to something that can fail: e.g. "adding a fourth Channel value requires zero changes in `Server`/`Projections`."

- **[critical]** Three cross-aggregate behaviours are required but have no owner under the purity rules (§4.4 FR-15/FR-16, §4.2 FR-10 cascade, §4.3 FR-13, §9 Domain purity, §4.7 FR-24) — `Handle` "never reads a clock or an outside system," yet: FR-16 says `ChildSpawned` "creates a child Work Item … and emits on the parent" (one command, two aggregates); FR-15 says "a child's `WorkItemCompleted` raises a resume command to a parent"; FR-10 says cancel "cascades … to its still-active descendants"; FR-13 rejects cycles and cross-tenant links, which requires reading the *other* aggregate. UJ-3 attributes this to "the engine," the addendum to "internally," and FR-24 forbids Works from owning "subscription plumbing." Two teams will build this differently: one puts a process manager in `Server`, the other relies on platform subscriptions and leaves a window in which a cancelled parent's child still accepts progress. Both claim compliance. *Fix:* Add an FR that names the process-manager/saga component, which package owns it, and its consistency guarantees (which aggregate is written first on spawn; whether cascade is synchronous or eventual; what a child does with `ProgressReported` after its parent is terminal but before the cascade reaches it).

- **[high]** The state machine has a transition with no event and a terminal state that isn't (§4.2 FR-6/FR-7/FR-10) — §4.2 opens with "every transition is a Raw-Act Domain Event," and FR-7 declares the catalog "final for v1." There is no event for `Assigned → InProgress` (no `WorkItemStarted`); an engineer must either infer the transition from the first `ProgressReported` (a status change with no dedicated act) or add an event the catalog forbids. FR-6 lists `Rejected` as terminal with "no transition … out of a terminal state," while FR-10 says after `WorkItemRejected` "the item returns to `Queued`" — either the event fires without entering the state, or a terminal state is exited. Reject is also undefined for `InProgress` (after partial progress) and for `Queued` (nobody is bound). *Fix:* Publish the full transition table (from-state × command → to-state × event) as the normative artifact, add `WorkItemStarted` or state that `ProgressReported` is the start act, and split "Rejected" into a requeue outcome (status `Queued`, event `WorkItemRejected`) and a terminal outcome.

- **[high]** "Done = Remaining is 0" is not one invariant but three completion paths, and the auto path is irreversible (§3 Burn-Down/Remaining, §4.2 FR-8/FR-9) — FR-8 auto-completes the moment Remaining hits 0; FR-8 also says an unestimated item "completes only by an explicit complete act"; FR-9 says `ReEstimated` "adjusts Estimated (and therefore Remaining)," so a downward re-estimate below Done silently completes the item. FR-9 also says "over-run and partial progress are native, not errors" — but an executor who reports the full estimate before actually finishing gets auto-completed into a terminal state (FR-6) and can never re-estimate. An estimated item with Remaining 3 cannot be explicitly completed ("never set independently of the burn-down"), so every client will implement "Complete" as a synthetic re-estimate-to-done — some emitting three events, some one. *Fix:* Decide whether Remaining=0 is a *precondition* for an explicit `Complete` (recommended: it keeps one completion act and one event) or an *auto-trigger*; if auto, add a `Reopen` transition or drop "over-run is native"; forbid `ReEstimated` below Done, or specify that it completes.

- **[high]** Resume idempotency is specified two incompatible ways, and the substrate dedup cited does not cover the case that matters (§4.4 FR-15, §10 Idempotency) — FR-15: "a resume whose key matches no current Await-Condition is a domain rejection, and a duplicate of an already-applied resume is an idempotent no-op." §10: "a resume whose key no longer matches an Await-Condition is a no-op." Distinguishing "already applied" from "never matched" requires the aggregate to retain every past Await-Condition. §10 then leans on "the substrate's command/event handling dedups replays by stream offset" — that dedups *event replay into projections*; an at-least-once timer adapter firing twice produces two distinct *commands* at two offsets, which no offset check catches. *Fix:* Pick one: (a) any resume with a non-matching key is a no-op (`WorkItemResumeIgnored` or empty result), or (b) it is a rejection and the aggregate keeps a bounded history of satisfied keys. State that duplicate-command idempotency is the aggregate's job, not the substrate's.

- **[high]** The Roll-Up requirements are mutually underdetermined and the "single number" promise is withdrawn by FR-12 (§1 Vision, §4.3 FR-11/FR-12, §11 SM-2) — Vision: "an objective's all-in remaining work is a single number." FR-12: mixed-Unit subtrees expose "per-Unit subtotals rather than a coerced single figure" — so the single number exists only when every descendant happens to share a Unit, and nothing prevents a child spawned in `tokens` under a parent in `hours`. FR-11 demands both "reflected incrementally" and "idempotent under at-least-once, possibly out-of-order event delivery"; delta-accumulation satisfies the first and fails the second, per-child last-known-Remaining snapshots satisfy both — the PRD does not say which, and the first is what gets written under deadline. SM-2 ("for any constructed Work Tree, rolled Remaining equals …") is unfalsifiable against an eventually-consistent projection with no convergence bound: any failing read is "stale but converging." *Fix:* Require the projection to store per-child last-known Remaining (state-based, not delta-based) and name the quiescence condition SM-2 is asserted under (e.g. after all published events are acknowledged, or within N seconds). Either constrain Unit inheritance at spawn or downgrade the Vision claim.

- **[high]** Expire smuggles a scheduler, an undefined "type" concept, and actor-less raw acts into a kernel that ships no adapters (§4.2 FR-10, §4.4 FR-15, §4.7, §13 OQ-4/OQ-6, §10 Audit) — FR-10: "Expire fires when the Due Date passes (or, absent a Due Date, a configured per-type TTL)." Who fires it? FR-15 says timers arrive as commands from "a timer/scheduler adapter," which OQ-4 defers to architecture and §4.7 says does not ship ("no production channel adapter"). SM-1 nevertheless requires date-triggered resume end-to-end. "Per-type TTL" and FR-13's "configurable per tenant/type" introduce a Work Item *type* that appears nowhere in the Glossary or FRs, plus a configuration source (OQ-6) that a pure `Handle` cannot read. And §10 defines a Raw Act as "acting Party + timestamp + verbatim payload" — a timer-fired `WorkItemExpired`, or a cascaded `WorkItemCancelled` on a child, has no acting Party; the non-repudiation model has a hole for every system-originated event. Finally, a parent Suspended on a child expires by its own Due Date and cascades `WorkItemExpired` onto a child that is 90 % done and not itself overdue. *Fix:* Add the timer/scheduler adapter to v1 scope explicitly (it is required by SM-1) and name its owner; define "type" or delete the two references; specify how configuration enters `Handle` (in the command, in state, or not at all — fixed constants); define the actor for system-originated events; state whether Expire is legal from `Suspended`.

- **[high]** v1's own scope statement contradicts itself and strands work (§0, §5, §12) — §0: "v1 (the foundation: Themes 1 & 2)." §5: "The brainstorm filed MCP-as-actor-channel and CLI-as-scriptable-work under foundation Theme 2; v1 deliberately defers even these." So v1 ≠ Themes 1 & 2, and the deferred Theme-2 items appear in no §12 roadmap row (Theme 3 is LLM-native; MCP/CLI are explicitly non-LLM). They are homeless, which is how deferred work becomes forgotten work. *Fix:* Restate scope as "Theme 1 + the kernel subset of Theme 2" and add a roadmap row (or a Theme 3 sub-row) for the non-LLM command surfaces.

- **[medium]** The "what's next" query has no defined consumer, and the September amendment replaced a wrong tiebreak with an arbitrary one and called it a decision (§4.6 FR-20, §4.1 FR-4, §13 OQ-2) — FR-20 returns "a tenant's claimable/assigned Work Items" — one list mixing everyone's `Assigned` items with the shared `Queued` pool. For whom is that "next"? An executor wants *my assigned + claimable*; a coordinator wants the pool. The amendment fixes the tiebreak to `WorkItemId` ordinal ("replay-stable strict total order") while conceding that approximating creation order is "guidance, not an enforced contract" — so two equal-priority, equal-due items are ordered by something no user can reason about. "applies query-side authorization/result filtering" names no criterion, and AuthorityLevel is unenforced, so filtering on what? Priority's type and direction (OQ-2) are deferred, so FR-4's "sorts last" is untestable. *Fix:* Split into two queries (per-executor and per-tenant pool) or add an executor parameter; name the filter predicate; commit to Priority's ordering direction now even if the type is deferred; if the id-ordinal tiebreak is acceptable, say so as a product decision, not a substrate accident.

- **[medium]** The thin core leaks at four visible seams (§4.2 FR-7, §4.6 FR-21/FR-22, §3 Obligation, §11 SM-C2) — FR-7: events "may carry an optional human-readable note"; FR-21: "Works holds the correlation ID rather than its own comment store." A note-per-event *is* a comment store. Obligation's "human-readable description" is unbounded, so a 10 KB markdown brief in the aggregate is compliant and Works becomes the "system of record for the content of work" §5 disclaims. FR-22 mandates `IExecutorRouter` with "no implementation wired" and no caller, and `IExpectationResolver` whose only implementation "returns an empty/structured default" — dead abstractions in the v1 domain, which SM-C2 calls "a negative" when anyone *else* does it. *Fix:* Bound the description length and forbid notes on events (or admit Works owns a minimal note stream and reconcile FR-21); drop `IExecutorRouter` from v1 (Theme 4 can add an interface additively — no event-schema issue applies to a C# port) and defer `IExpectationResolver` until it has a non-trivial caller.

- **[medium]** The Success Metrics are a test plan, and two of them are unmeasurable (§11) — SM-1 through SM-5 restate FR consequences as "demonstrated by test." SM-4's "zero duplicated technical/infrastructure layers" and SM-C1's "lines/surface … should not be maximized" have no measure, threshold, or reviewer. Nothing measures the JTBD the PRD opens with — a builder other than the author wiring Works into a module (UJ-1) — so a v1 nobody consumes passes every metric. §9 Performance concedes "no numeric targets," which is honest but leaves FR-11's "responsive for realistically deep/wide trees" unfalsifiable. *Fix:* Add one adoption signal (a second Hexalith module consumes Works without a kernel change) and one shape budget (e.g. `Contracts` public-type count, or `Server` LOC ceiling) so SM-C1 can actually fire; give FR-11 a single indicative budget (depth 32 × fan-out 100, rolled read < X ms) marked provisional.

- **[medium]** September amendments are inconsistently marked and the "all resolved in June" claims are now false (frontmatter, §4.2 FR-7, §4.6 FR-20/FR-21, §13, §14) — Frontmatter says `updated: 2026-09-05`; FR-20 says "Amended 2026-09-06." FR-20 is the only text marked as amended, yet the `LinkConversation`/`ConversationLinked` first-link-authoritative rule in FR-21 (and the corresponding sentences in FR-7 and the addendum) is written at a precision nothing in the June text approaches and is absent from §14's FR-21 entry, while §14 asserts "All confirmed by the user on 2026-06-14." §13 claims the eight draft OQs "were resolved on 2026-06-14" — VAL-H03 shows requirements defects continued to surface. The FR-21 rule itself is unjustified: binding, schedule, and estimate are all mutable; why is the Conversation link the one immutable fact ("attempting to replace it with a different ID is a domain rejection")? *Fix:* Add a change log section listing each amendment with date and rationale; mark every amended sentence; update §14 and the frontmatter date; state why a Conversation is single-and-immutable or allow relink with a `ConversationUnlinked` event.

- **[low]** Why Now argues for the synthesis and v1 ships none of it (§7) — "the whitespace is the synthesis — one audited object where the backlog, the durable saga, and the effort+cost ledger are the same thing." v1 has no cost ledger, no interpretation, no routing, and no channel; the timing argument justifies Themes 3–6, not a headless kernel. As written it gives an architect no reason to prefer shipping v1 over shipping a thinner Theme-3 spike that would actually test the bet. *Fix:* Either state the v1-specific timing pressure (e.g. a named sibling module blocked on Works) or move §7 to the brief and replace it with one sentence.
