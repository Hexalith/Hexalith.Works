## Critical findings

### ADV-U1 — AD-06 and AD-22 jointly specify two incompatible roll-up shapes

**Severity:** Critical (two register entries conflict; "the register wins" cannot arbitrate between register entries)

AD-06 binds the recursive shape: contributions keyed `(childId, childEventSequence)`, `rolled = own + Σ per-child rolled`, and the document's own good-pattern example locks it in — `contributions[childId] = (childSequence, childRolledRemaining)` (`architecture.md:828`). That is a **per-direct-child slot holding the child's *rolled* value**. AD-22 binds the delivery: on a child's event, the fan-out "writes the child's contribution into **each ancestor's** roll-up document using the AD-06 per-`(childId, childEventSequence)` LWW slots," with "Inputs: the child event plus registry ancestry" (`architecture.md:288-298`). That is a **flattened per-descendant slot holding a value computable from the event alone** — i.e., the descendant's *own* contribution, because the child's rolled value (own + its descendants) is not derivable from one event plus an ancestry list.

**Two-unit counterexample (interface halves, matrix R4).** The EventStore SDK team builds the generic fan-out exactly as AD-22 reads: for child event `(C, seq S)` resolve ancestors `[P, G]`, write slot `(C, S) → own-contribution(C)` into P's and G's documents. The Works team builds the pure merge strategy exactly as AD-06/`:828` read: each document holds direct-child slots carrying rolled values, `rolled = own + Σ child.rolled`. The halves do not fit: the SDK hands G a slot for grandchild C that the strategy's schema says must be a slot for direct child P carrying P's rolled value — which neither the event nor the ancestry supplies. Both teams cite their AD verbatim.

**Same hole, single-team form.** Under the recursive reading, a grandchild event at sequence 12 must update the grandparent's slot for the *middle* child — keyed by whose sequence? The middle child's own events write that slot with middle-child sequences; the grandchild's propagation writes it with grandchild sequences. LWW across two independent stream-sequence spaces is meaningless: `(P, midSeq=5, rolled=8)` vs `(P, gcSeq=12, rolled=9)` has no defined winner, so redelivery permutations no longer converge — the exact RR-1 corruption AD-06 exists to prevent, reintroduced one level down.

Note the flattened reading is self-consistent: every slot `(descendantId, descendantSeq)` is written only by that descendant's own event stream, LWW within one sequence space is well-defined, and `own + Σ descendants' own` equals the recursive total. The recursive wording and the `:828` example are what make the register two-valued.

**Binding required (tighten AD-06 + AD-22 together):** pick one document shape — recommend flattened per-descendant own-contribution slots — and state it as the slot's key *and value* semantics: "each roll-up document holds one LWW slot per descendant (not per direct child), keyed by that descendant's id and its own envelope `SequenceNumber`, valued with that descendant's own-contribution per Unit; `rolled = own + Σ slots`." Retire or rewrite the `rolled = own + Σ per-child rolled` phrasing and the `:828` example, and add the FsCheck convergence property over ≥3-level trees to the RR-1 gate.

### ADV-U2 — The reserve→spawn failure lifecycle is unbound; AD-21's disagreement rule then makes the wrong fact authoritative

**Severity:** Critical (two owners of one entity's existence; the bound tie-breaker picks the non-existent one)

AD-21's happy path is clear: registry `Handle` reserves the edge (edge-reserved event), then the mechanical reactor drives `SpawnChild` on the parent (`architecture.md:270-276`). But `ChildSpawned` on the parent stream is not a mere edge record — it is the **child's creation event**, carrying Obligation, InitialEffort, Schedule, ExecutorBinding, ConversationCorrelationId (`src/Hexalith.Works.Contracts/Events/ChildSpawned.cs:8-19`). And the parent's `Handle` legitimately rejects `SpawnChild` from terminal or wrong states (`src/Hexalith.Works.Server/Aggregates/WorkItemAggregate.cs:80-87`). So the race the prompt names is real and *ordinary*: parent goes terminal (cancelled/expired/completed) between edge reservation and `SpawnChild` handling. Result: a registry-accepted edge for a child **that was never created at all**.

No AD binds what happens next, and the bindings that do exist point the wrong way:

1. **AD-21 repair semantics misclassify the race.** "When registry and item-stream evidence disagree, the registry stream is authoritative," and rebuild-detected asymmetry "suppresses dependent roll-up/cascade … until an audited operator repair." A routine concurrency race — the same class of race AD-08 resolves with an automatic domain rejection — is routed to *audited operator repair*, and the tie-breaker crowns the registry's ghost edge over the item streams' truth that no child exists.
2. **Cascade now consumes the ghost.** Post-AD-21/AD-22, descendant enumeration comes from the registry. A compliant cascade unit cancelling the terminal parent's subtree emits `CancelWorkItem` at a never-created aggregate; no AD defines the outcome (create-less cancel ⇒ rejection loop? checkpoint `Completed` on submission? dead-letter?). Builder A's cascade skips unknown aggregates; builder B's counts the rejection as completion; builder C's retries forever. All compliant.
3. **Mechanical compensation is currently inexpressible.** The natural fix — reactor translates the spawn rejection into a registry `ReleaseEdge` — fails on the existing contract: the rejection is `WorkItemTransitionRejected(TenantId, WorkItemId, FromStatus, AttemptedAct)` (`src/Hexalith.Works.Contracts/Events/Rejections/WorkItemTransitionRejected.cs:17-21`) and carries **no `ChildWorkItemId`**, so no pure `react(event) → command[]` can name the edge to release (AD-10 forbids the reactor looking anything up). An additive rejection type carrying the child id is permitted by the evolution rules — but nothing requires it, and a second builder ships without it.
4. **Duplicate-delivery interaction.** If a builder does wire rejection→release, an at-least-once redelivery of the edge-reserved event re-drives `SpawnChild` at a parent that already spawned the child; nothing makes duplicate `SpawnChild` a no-op (AD-13 covers only `ResumeWorkItem`), so the duplicate is rejected — and the compensating reactor releases a **healthy** edge. The only guard is transport dedup by deterministic MessageId, which is precisely the open VAL-H10 seam. AD-21 has silently made VAL-H10 load-bearing *before* its stated revisit condition (R3 acceptance / Theme 3).

**Binding required (tighten AD-21):** bind the full attachment saga, not just its first leg — (a) reservation state is explicit (`Reserved` → `Attached` on `ChildSpawned` evidence | `Released` on rejection/timeout), with a bounded reservation TTL; (b) a dedicated additive rejection event carrying `(TenantId, ParentId, ChildWorkItemId)` so release is mechanically translatable; (c) duplicate `SpawnChild` for an already-attached identical `(parent, child)` is a defined **no-op**, not a rejection; (d) cascade and fan-out enumerate only `Attached` edges — `Reserved` edges are invisible to both; (e) restate the disagreement rule as "authoritative for *topology among existing items*" so a registry edge whose child stream has no creation event resolves automatically to `Released`, not to operator repair. Also state the VAL-H10 dependency explicitly on AD-21 (deterministic causation ids for the reserve→spawn→release translations) or accept (a)-(d) as sufficient without it.

## High findings

### ADV-U3 — Direct `SpawnChild` submission bypasses the registry and no AD closes the door

**Severity:** High (an enforcement point the owning story could add — but today two ADs jointly authorize the bypass)

AD-21's Rule says "no unit mutates tree shape except through the registry protocol." But `SpawnChild` remains a public catalog command (`architecture.md:693-696`), its caller-fed topology facts keep their permissive defaults as "assertions," and the parent's pure `Handle` cannot tell reactor-originated from caller-originated commands. AD-23's minimum authorization explicitly admits it: "commands ⇒ authenticated member of the target tenant" (`architecture.md:322-324`). AD-24's exclusive-originator list restricts topics, reminder callbacks, and replay — **not per-command gateway submission** (`architecture.md:337-342`).

**Two-unit counterexample:** the platform ingress team accepts `SpawnChild` from any tenant member (AD-23-compliant); the registry team assumes every `SpawnChild` was preceded by a reservation (AD-21-compliant). A tenant member submits `SpawnChild` directly with default assertions; the parent accepts (the demoted guard sees nothing wrong); an edge exists in the item streams that the registry never reserved — ADV-01's dual-parent hole returns through the front door, now *worse*, because AD-21 declares the registry (which knows nothing) authoritative and roll-up/cascade enumerate from it: the directly-spawned child is invisible to ancestors until an operator rebuild.

**Binding required:** name the enforcement point — either `SpawnChild` (and any future registry-internal command) is restricted to the reactor's workload identity at the gateway (extend AD-24's exclusive-originators to command-type → originator-identity pairs), or the public entry point is renamed to a registry command (`AttachChild`) and `SpawnChild` is removed from the public catalog. Add the negative test to the AD-24 suite: direct `SpawnChild` under an ordinary tenant-member identity is denied.

### ADV-U4 — "Unresolvable ancestry ⇒ no ack" cannot distinguish a root from a lagging registry projection

**Severity:** High (a protocol rule the owning fan-out story could settle; both compliant readings are defective)

AD-22: ancestors are resolved from the registry *read model*; "unresolvable ancestry ⇒ the delivery is not acknowledged and is redelivered" (`architecture.md:290-296`). The registry read model is itself an eventually consistent projection of the registry stream. When a child's event arrives and the read model shows **no edge**, that is two indistinguishable states: (a) the item is a genuine root — empty ancestry, correctly resolved, fan-out is a no-op; (b) the item was attached, but the edge-reserved/attached event has not yet reached the registry projection.

**Two-unit counterexample:** Builder A reads "no edge = resolved as root" and acks — in case (b) the ancestor slots are silently never written for this event, and because AD-06 slots are per-event LWW, nothing retries; ancestors under-roll until the child's *next* event, which may never come (a completed child's final `ProgressReported` is exactly the event that matters). Builder B reads "no edge = unresolvable" and nacks — every event of every genuine root item redelivers forever: livelock, dead-letter floods, and under AD-22's own rule the ordinary path now *requires* operator action, which the Rule prohibits. Both cite AD-22 verbatim.

**Binding required:** give the fan-out a freshness witness. Cheapest consistent option: the registry answers ancestry queries with its own stream position, and every child item carries its attachment provenance — e.g., `ChildSpawned`/the child's creation evidence records the registry sequence of the reservation, so the fan-out rule becomes "resolved iff the registry read model's watermark ≥ the child's attachment registry-sequence (or the child verifiably has none — created via root `CreateWorkItem`)." Roots resolve immediately; lagging edges nack-and-retry with guaranteed progress. Bind it in AD-22 alongside the AD-16 note that fan-out writes during a staged rebuild follow the fence (VAL-H08) rather than racing the staged generation.

### ADV-U5 — The registry event ↔ reactor `SpawnChild` translation is only mechanical if the reservation carries the whole creation payload

**Severity:** High (contract-shape decision the registry story could settle; two teams will otherwise ship incompatible halves)

AD-10 requires `react(event) → command[]` to be pure translation with no lookups. AD-21 requires the reactor to drive `SpawnChild` from the edge-reserved event. But `SpawnChild` needs the full child-creation payload — obligation, initial effort, schedule, executor binding, conversation link, suspend-parent flag (`src/Hexalith.Works.Contracts/Commands/SpawnChild.cs:19-32`) — plus the registry-derived assertion values AD-21 says replace caller facts. Therefore the registry's reservation command/event must carry **all of it**, duplicated into a second durable contract family, or the reactor cannot be mechanical.

**Two-unit counterexample:** the registry team ships a minimal topology contract — `ReserveChildEdge(tenant, childId, parentId)` / `ChildEdgeReserved(...)` — because AD-21 scopes the registry to owning "edges … ancestry and depth." The reactor team, forbidden to look anything up, cannot construct `SpawnChild` from it; their compliant fallback is to have the *caller* pass the payload straight to the parent — which is ADV-U3's bypass. Alternatively the reactor team demands the fat event while the registry team refuses payload it doesn't validate. Both positions are AD-compliant.

**Binding required:** state in AD-21 that the reservation command/event carries the complete `SpawnChild` payload verbatim (raw-act: reported values, uninterpreted) plus the registry-derived ancestry/depth snapshot the parent will receive as assertions; list the registry types in the durable catalog count and golden corpus explicitly.

### ADV-U6 — No identity is authorized to register or cancel expiry reminders in the production topology

**Severity:** High (one sentence in AD-24 fixes it; today two compliant teams strand expiry silently)

AD-25 says expiry reminders are "registered, cancelled, and rescheduled mechanically from lifecycle events … by the reminder adapter" (`architecture.md:354-359`). Registration is a Dapr actor-reminder operation invoked from wherever lifecycle events are consumed (post-migration: the SDK delivery pipeline, R3/R6). Now cross-check the security ADs: AD-24's exclusive-originator list covers `work.events` publication (EventStore only), reminder **callbacks** (Works actor identity only), and replay/rebuild (operations identity) — it never names an identity allowed to invoke reminder **registration/cancellation** on the actor. AD-23's internal-originator delegation list enumerates "reactor, reminder callbacks, replay, recovery" — the reminder *registrar* is not a reactor (it emits no commands; it calls an actor API) and not a callback.

**Two-unit counterexample:** the platform team implements AD-24 to the letter — deny-by-default app access control, "no direct workload HTTP reachability to … actor … routes," allowlist exactly the named originators. The Works/SDK team implements AD-25 to the letter — the event processor registers the expiry reminder on `WorkItemCreated`. In production the registration call is denied by policy; every acceptance test passes in the sandbox because AD-24 expressly permits relaxing named controls under the dev-only exemption. Expiry never fires in production; AD-12 ("advisory-until-fired") makes the failure invisible to the kernel and every query. The reconciliation pass (AD-11/R6) runs under the same unlisted identity and is equally denied.

**Binding required:** extend AD-24's exclusive-originators with the registration direction — "actor reminder register/cancel/reschedule is accepted only from the Works service's own workload identity (self-targeted), and the delivery-pipeline component that performs it is enumerated in AD-23's delegation list" — and add the positive-path production-policy test (reminder registered under production access policy) to the R6/R10 proof set, since every listed AD-24 test today is negative.

### ADV-U7 — Matrix rows leave two live runtime capabilities without an owner or a proof

**Severity:** High (the matrix is AD-20's binding artifact; its Rule keys removal to "the corresponding row" — capabilities with no row have no removal gate)

Checked against the actual folders (`src/Hexalith.Works/Runtime`, `Projections`, `Reminders`, `Recovery`):

- **Child-completion resume recovery has no row.** `src/Hexalith.Works/Recovery/ChildCompletion/` (`WorkItemCompletedResumeHandler.cs`, `ChildCompletionResume.cs`, `StreamReadingChildCompletionAwaitingParentSource.cs`) is a recovery flow distinct from cascade: it re-discovers parents awaiting a child completion that was published while the processor was down. R7's seam column reads "**Cascade** dispatch, checkpoints, recovery" — a platform builder migrating strictly by row moves cascade and leaves child-completion recovery behind; the Works builder deletes `src/Hexalith.Works/Recovery/` as "R7 green." That is the precise double-abandonment AD-20's Prevents clause names. R6 doesn't cover it either (it is not a reminder flow). Fix: widen R7 to "cascade **and child-completion resume** dispatch/recovery" and add the missed-child-completion crash scenario to its proof column.
- **The command-submission seam has no row.** `IWorkCommandSubmitter`/`EventStoreGatewayWorkCommandSubmitter` (`src/Hexalith.Works/Runtime/EventStoreGatewayWorkCommandSubmitter.cs:14-34`) is the shared seam through which *every* internal originator (reminders, cascade, child-completion — and soon the AD-21 reactor) submits commands with deterministic `MessageId`/causation. R3 covers inbound subscription/processing, R6/R7 cover the flows, but the outbound submitter — the very seam VAL-H10 says idempotency must be bound at — is allocated by no row. Two builders can put it in the SDK (generic gateway client) or keep it in Works (domain causation derivation) and both cite the allocation rule. Fix: add a row (or extend R3) naming the submitter seam, its target owner (SDK client + Works-owned deterministic-causation policy), and the VAL-H10 binding as its proof.

Also checked and found covered: `WorksHost`/`WorksRecoveryExtensions` (R2/R9), `WorksDomainEventProcessor`/decoder/endpoints (R3), `WorkItemProjectionDispatcher`/`SharedRebuild`/`WorksReadModelKeys` (R4), the reminder family (R6), cascade family (R7). The cross-tenant `PendingDateAwaitTenantRegistry` and `WorksWhatsNextTenantIndex` fall under open VAL-H09 (deliberate deferral — no new finding).

## Deliberate deferrals verified (no new findings; downgraded per the open register)

- **Fan-out vs staged generation (AD-22 vs AD-16):** an ordinary fan-out write racing a staged generation is exactly the capture-through-Commit fence problem; the document already carries it as VAL-H08, allocated to R4. The LWW slot design means post-Commit catch-up converges *provided the fence redelivers* — worth one sentence in AD-22 ("fan-out writes are fenced writers under AD-16"), but the substance is deferred, not missed.
- **Cascade checkpoint concurrency under replicas:** VAL-H06, bound at R7. ADV-U2's ghost-edge interaction adds a new *input* to that spec (registry-enumerated descendants) — flag to the R7 spec owner, not a new register hole.
- **Transport idempotency:** VAL-H10 — but note ADV-U2/4: AD-21 quietly advances its due date; the open register's "before Theme 3 / R3 acceptance" revisit condition is now too late if the registry story lands first.
- **Namespace/ownership table:** VAL-H09 covers the registry's new keys (registry aggregate id, registry read-model/watermark keys) — the registry story should extend that table, not invent names.

## Gate conclusion

The 2026-09-05 macro non-convergence is genuinely repaired: tree attachment, roll-up delivery, and host migration each now have one named owner, one protocol direction, and a proof lane. What remains is one level further down, concentrated where the prompt aimed: the *interior* of AD-21/AD-22. ADV-U1 and ADV-U2 must be closed by tightening the register (AD-06/AD-22 slot semantics; AD-21 saga lifecycle) **before** the registry and fan-out stories are drafted, because both stories would otherwise inherit a two-valued contract. ADV-U3…U7 are each closable with a sentence-to-paragraph amendment in AD-24, AD-22, AD-21, and the AD-20 matrix respectively, and could acceptably be folded into the owning stories' entry criteria if the register cross-references them.
