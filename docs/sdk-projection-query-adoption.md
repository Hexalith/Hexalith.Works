# Works SDK projection and query adoption (Story 4.14)

## Mode and ownership

`Works:Projection:UseSdkDelivery` defaults to `false`. In that mode Works keeps its existing `/project` writer, schema-v2 and legacy readers, and reminder and Reactor composition. Set it to `true` only in an isolated migration fixture: the host disables the bespoke writer, exposes the EventStore named epoch handler for `works-runtime-v3`, and selects SDK generation reads for queries, reminder discovery, and cascade descendants. The handler's projection type, scope family, and control index all identify that one runtime family. EventStore owns lease fencing, journal, physical generation keys, checkpoints, promotion, abort, and read selection. Works returns logical batch operations after folding domain evidence.

In SDK mode Works maps no `/project` handler. An authenticated request to that retired legacy route reaches the canonical SDK, which answers `404`; a request without the receiver's channel credential is still refused with `401`. The `404` closes the gateway's pending legacy replay intent, so later named deliveries on `/project/v2` are not delayed. Works must not replace it with a custom status: a `409` leaves the gateway's legacy replay intents frozen and delays every subsequent named delivery. `WorksSdkProtectedHttpTests` covers the status codes and the replay-intent behaviour in process. Live, the Story 4.16 Platform verifier proves less: posting directly to the Works app port on the Platform host, a credentialed request gets `404`, an uncredentialed one gets `401`, and the accepted family stays unchanged.

The runtime family holds a tenant queue and membership index, per-item roll-ups, relationship topology, pending-date entries and cleared-await sequence tombstones, per-item parking records, and source context used to fold individual SDK envelopes. A rebuild stages those documents as one manifest. It leaves the pre-cutover schema-v2 and legacy keys intact for full restore. An incomplete, malformed, gapped, or conflicting candidate fails before promotion. Ordinary delivery uses the same fold to update the selected generation; duplicate deliveries do not logically advance the checkpoint twice. `Works:Projection:MaxUndecodableEventDispatchesBeforeParking` remains the bounded terminal parking threshold.

## Query authority

SDK `/query` ingress accepts only the authenticated EventStore gateway workload named by `Works:Query:GatewayWorkloadId` (default `eventstore`). The gateway must stamp the authenticated workload and original actor fields. Works uses the published Parties client to resolve the requested `partyId` under the exact query tenant and actor; the client is registered at the host edge and calls the canonical Parties gateway. Configure `Works:Query:PartiesGatewayBaseAddress` as an absolute URI, or provide `EventStore:CommandGateway:BaseAddress`. Supply independently provisioned service authority through `Works:Query:PartiesGatewayBearerToken` using the host's secret configuration (environment key `Works__Query__PartiesGatewayBearerToken`), or configure the typed client's outbound Authorization header at the host edge. The authorization handler requires that outbound service bearer and never forwards the inbound request's `Authorization` header (on SDK ingress it is the gateway workload assertion minted for Works); absent a bearer the Parties call fails and the query is denied. It never obtains credentials from the query payload. An unparsable Parties base address fails host startup in SDK mode, and a failed Parties resolution is logged as a warning before the query is denied. Missing, expired, or rejected authority denies before any Works state read. A caller's `UserId`, payload role, or `IsGlobalAdmin` flag is insufficient. The EventStore producer strips human `Authorization` on canonical invocation, so normal SDK Executor ingress requires independent service authority. Platform reader admission must explicitly allow that independently authenticated service identity. The synthetic composition below verifies that path; production provisioning remains gated.

Verified Executors may read their own Assigned work and the tenant's Queued work. Full tenant results require an exact workload in `Works:Query:PermittedCoordinatorWorkloads`; its default is empty. Neither the Platform Works preview nor the retained Works AppHost configures it, so the Story 4.16 Platform verifier sends every live restart, rollback, rebuild and quarantine query as a delegated Executor query: gateway workload `eventstore`, `IsDelegated`, the original actor as both actor and user, and only the Executor `partyId` in the payload, resolved by a test-only Parties identity authority. Each live lane therefore keeps one item Assigned to that synthetic Executor, and a non-delegated full-tenant workload query is recorded as `Forbidden` on a Platform start. Related documents are read from one SDK selected generation. Responses mark prior-generation data stale and failed generation reads unavailable. Reminder recovery discovers tenants from the SDK control index, reads pending and parking documents from one selected generation, and still refolds each candidate's authoritative stream. Cascade recovery retains its authoritative stream read and pins queue, roll-up and parking together; degraded, stale, unavailable or parked evidence leaves children conservatively active. Reminder discovery propagates degraded family readiness through its existing incomplete-scan result.

## Migration and rollback

This story does not authorize production activation. Before any later cutover, capture a restorable point-in-time copy of the **entire** EventStore/Works state store, its activation marker, projection metadata, journals, checkpoints, source events, and the compatible fleet/configuration; retain the replay source and verify the restore in an isolated environment. Quiesce the old Works delivery path at the migration fence, deploy one SDK writer and matching readers together, capture the sealed tenant inventory, stage and promote the full family, and check control-index membership, checkpoint heads, parking/readiness, and query freshness before admitting traffic. Abort a failed candidate and keep the previous generation serving marked-stale reads. Do not run old and new writers against the same live tenant.

The EventStore v2 activation marker prevents an in-place downgrade. Rollback restores the **complete pre-cutover store and fleet snapshot together**, including the marker and all projection/control/checkpoint data, then replays retained source events through the pre-cutover writer and verifies legacy read models before reopening traffic. Merely switching `UseSdkDelivery` off against a v2-activated store is not rollback. Any production marker, deployment, real authority provisioning, and Platform R3–R5 admission remain gated by Story 4.16 and AD-28.

## Legacy development host credentials

The AppHost keeps legacy delivery as the default. In run mode it gives every Dapr application a unique secret application-channel parameter, shared only with its own sidecar through `WithGeneratedEventStoreAppChannelToken`. Child projects explicitly inherit the AppHost environment. With `--EnableKeycloak=false`, EventStore, admin and Works share a secret Aspire JWT parameter for the SDK issuer/validation contract, while the SDK still checks the receiving workload audience, caller, operation and resource bindings. The local key is generated per run unless supplied through secret configuration `Works:Authentication:DevSigningKey`; live smoke fixtures supply an explicit synthetic key. Symmetric validation retains the SDK's Development-only restriction. Publish targets must supply their own secret material and remain outside this story's admission.

With symmetric development credentials, the recovery gateway client uses SDK workload transport with one signed operation/audience/tenant/domain grant per request. With `EventStore:Authentication:Authority`, it uses the ordinary protected command and stream endpoints and the SDK's authority access-token handler. `WithEventStoreClientCredentials(security)` binds the same realm-owned secret username/password parameters to Keycloak and Works; Works does not invent a separate password. Token acquisition requires an explicitly configured endpoint within that authority, HTTPS outside Development, an explicit password or client-credential grant, no redirects, and a bounded response. The canonical gateway retains normal JWT validation, tenant and RBAC authorization. Failed acquisition has no unauthenticated fallback.

The real Works client composition and SDK credential tests execute both command and stream calls against synthetic HTTP authority/gateway boundaries. This does **not** establish a live imported Keycloak realm: Works currently imports the raw EventStore `KeycloakRealms/hexalith-realm.json`, which still contains `__HEXALITH_*` user/password/client-secret templates and no realm-bound generated client user. The Aspire helper passes secret parameters to the container but does not materialize those templates. Real realm materialization/provisioning is therefore a concrete authority-branch verification blocker; no successful live Keycloak credential exchange is claimed. Legacy mode advertises its shared rebuild route without advertising it for ordinary named delivery; SDK mode advertises `works-runtime-v3` for ordinary delivery. Both modes retain the shared rebuild API. The Dapr ACL permits EventStore's exact POST `/admin/operational-index-metadata` route so discovery can reach the legacy writer. SDK service defaults partition resilience by the configured Dapr target as well as sidecar authority; absent-module probes therefore cannot open Works' delivery circuit.

EventStore durably retains same-position conflicting identities in its existing fenced epoch state, covering pending journal entries, completed receipts, and captured event identities. Accepted family contents and checkpoints remain unchanged. Both single and related SDK reads expose `IsDegraded`; Works list and detail queries return unavailable metadata while that signal or the subsequent epoch status is degraded. Conflict redelivery is idempotent. A successful stage/promotion or abort does not erase evidence. After a **newer**, fully promoted and drained authoritative rebuild captures every affected source position, explicitly call `SharedProjectionEpochCoordinator.ResolveDeliveryConflictsAsync(scope, operationId)`; its resolution audit stays in epoch state. A conflict observed after that capture requires another covering rebuild.

The evidence is bounded to 128 identities with a reserved overflow disposition. Epoch writes reserve 8 KiB for emergency evidence. The first count/byte overflow durably degrades readiness and preserves the rejected identity; further unknown overflow cannot be acknowledged. A legacy epoch that already consumed the reserve reports degraded readiness even if new evidence cannot fit. Overflow requires complete scope restore or offboarding; the repair API refuses to discard this audit. Ordinary authoritative repair applies below that capacity bound.

Future owner-sequence gaps also persist in the same bounded SDK evidence before returning retryable delivery. No missing-prefix acknowledgement or checkpoint advance occurs. Readiness remains degraded across restart until the missing prefix and the exact previously rejected envelope have been successfully folded; that ordered catch-up resolution remains in the evidence record. Contradictory lower owner ordinals at new envelope positions are durable identity conflicts and require authoritative repair. The named-dispatch regression covers the real nonzero owner sequence both in memory and through a fresh Dapr/Redis client.

The corrected SDK fences owner-sequenced ordinary delivery while capture builds and during owner handoff. Those requests remain retryable without acknowledgement or checkpoint advance; the prior generation remains marked stale. After promotion and captured-owner seeding, retries converge through the sole SDK writer. The concurrency fixture verifies this supported producer contract instead of assuming delivery may advance owner checkpoints during capture.

## Ordinary growth and capacity recovery

Ordinary delivery computes a deterministic family but returns only changed logical values, keeping mutation count independent of total membership. Ordered source histories use 64 KiB logical pages and a length/digest manifest; readers also accept the previous inline context and convert it on the next successful delivery. These are plain host records, not durable domain catalog entries. The SDK remains the only physical writer and commits prepared mutations and the checkpoint through its existing fence.

The operational context bounds are 4 MiB per aggregate and 16 MiB per tenant, independently of the configurable rebuild-candidate transport budget. A delivery also remains subject to 128 changed mutations and the SDK's 256 KiB individual mutation limit, with reserved serialization overhead. A valid delivery exceeding any bound stays journaled with durable `ReasonCode=capacity`; it never consumes the corrupt-event retry count or becomes terminal poison. The previously materialized family remains intact and the journal-accepted checkpoint disposition remains durable; capacity retries do not advance it again. Pending capacity, unresolved parking and identity evidence prevent current/clean reads across restart. The capacity retry counter is capped independently; a later real fold failure starts its own retry budget.

A capacity alert requires an operator to retain the pending delivery and source history, deploy a compatible increased bounded context/partitioned representation through the same SDK writer, and retry the head before admitting traffic. A covering authoritative rebuild can repair bad-source parking only when complete source context and configured candidate budgets fit; replaying identical over-capacity history is not a repair. If that representation change is unavailable, keep the scope unavailable or offboard it, or use the already documented complete pre-cutover store/fleet restore and retained-source replay. Do not skip the event, clear the journal, truncate history, or switch writers against an activated store. These finite limits remain an explicit operational constraint.

First-delivery poison now records unresolved source/position/epoch parking evidence in the same SDK epoch CAS even before Works membership exists. The control-index tenant remains discoverable after unrelated healthy delivery and restart; list/detail return unavailable. Only an explicit newer covering promoted/drained authoritative repair resolves that audit. Parking uses the same reserved overflow/fail-closed capacity policy as delivery conflicts.

## Explicit Platform JWT reader admission

Platform retains its existing Dapr writer/provisioning and Dapr reader rules. Its new JWT path applies only to current `ResolvePartyIdentity` reads. Configure both a reader source and the independently authenticated service identity, for example:

```json
{
  "PlatformIdentity": {
    "ReaderSources": ["works-reader"],
    "JwtReaders": [{
      "SourceId": "works-reader",
      "Issuer": "https://identity.example/realms/synthetic",
      "Subject": "service-account-works",
      "ClientId": "works",
      "ClientIdClaimType": "azp",
      "AuthenticationType": "AuthenticationTypes.Federation"
    }]
  }
}
```

The existing canonical gateway JWT validator authenticates issuer, audience, signature, and lifetime. Platform matches issuer, subject, and client claims from one authenticated identity against that explicit configuration and checks expiry again. Tenant/RBAC validation remains mandatory. Arbitrary human subjects, payload roles, forwarded identity headers, and a source name alone cannot enroll a reader. The exact tenant/Party/operation/correlation/payload digest is signed only after a current active canonical actor registry entry is verified. The Parties authority verifies that exact signature, folds the authoritative Party source, checks the binding interval and policy, and consults current custody. Existing organization and historical inactive-actor Dapr reads retain their earlier semantics.

`WorksSdkProtectedHttpTests.ProtectedExecutorUsesCanonicalGatewayAndRealPlatformReaderAdmission` exercises protected Works `/query`, the **real canonical** EventStore `QueriesController`, JWT authentication, actual Platform reader admission, registry proof signing/verification, the published Parties client, and the existing Parties authority/query service/source folds. The non-packable Parties runtime sources are linked unchanged into the test assembly from root-declared `references/Hexalith.Parties` at the recorded revision; this source fixture is distinct from the published client/Contracts artifacts. Synthetic fixtures supply only complete authoritative event history, current registry evidence, and custody provider data. Missing/expired/untrusted/disabled readers, inactive actors, mismatched or expired bindings, and unsafe/unavailable custody deny before Works state access. Payload privilege hints never expand Executor results.
